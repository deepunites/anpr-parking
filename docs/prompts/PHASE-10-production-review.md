# PHASE 10 — Production review

**Предусловие:** gate фазы 9 пройден.

Эта фаза не добавляет функциональность. Она проверяет, что система действительно готова, и производит документы, без которых её нельзя эксплуатировать.

## 1. Runbooks

`docs/RUNBOOK.md`. Каждый сценарий по единой структуре:

```
Обнаружение      какой алерт, какой дашборд, какой лог-запрос
Влияние          что не работает для водителя, оператора, бизнеса
Немедленное      что сделать в первые 5 минут
Диагностика      команды с ожидаемым выводом
Восстановление   пошагово, с проверкой после каждого шага
Проверка         как убедиться, что починилось
Откат            что делать, если восстановление ухудшило ситуацию
После инцидента  что собрать, кого уведомить, что исправить
```

Обязательные сценарии:

1. PostgreSQL primary недоступен.
2. Лаг синхронной реплики растёт / реплика отвалилась.
3. Redis недоступен.
4. Шлагбаум не открывается на конкретной площадке.
5. Камера не присылает события.
6. Платёжный провайдер недоступен.
7. Накопление DLQ.
8. Лаг outbox растёт.
9. Двойное списание у клиента.
10. Расхождение сверки в пользу провайдера.
11. Подозрение на компрометацию ключа камеры.
12. Подозрение на утечку данных tenant.
13. Диск PostgreSQL заканчивается.
14. Провалившийся деплой, откат с применённой миграцией.
15. Массовое зависание сессий в `MANUAL_REVIEW`.

**Проверка качества runbook:** он должен быть выполним человеком, не участвовавшим в разработке. Каждая команда — копируемая, каждый ожидаемый вывод — приведён. Runbook с фразой «проверьте состояние системы» не принят.

Прогони минимум 3 runbook'а на staging, вызвав отказ искусственно, и вставь фактический лог прохождения.

## 2. Threat model

`docs/THREAT_MODEL.md`. Для каждой угрозы:

```
Угроза · Вектор · Влияние · Вероятность · Митигация (где в коде) · Детектирование (какая метрика/лог) · Восстановление
```

Угрозы из §59 исходного ТЗ — минимум. Добавь обязательно:

- Сговор оператора и водителя (ручное открытие, коррекция номера, наличная оплата мимо кассы).
- Подмена `event_time` камерой для занижения стоимости.
- Массовая генерация событий с валидным ключом одной камеры (DoS и фальсификация занятости).
- Подмена `image_object_key` для доступа к чужим изображениям.
- Компрометация ключа шифрования одного tenant.
- Инсайдер с доступом к БД: что он увидит, если получит дамп (ответ обязан быть «зашифрованные номера, не поддающиеся массовой расшифровке без Vault»).
- Подделка вебхука платёжного провайдера.

Для каждой митигации — ссылка на файл и строку, где она реализована. Митигация без ссылки считается отсутствующей.

## 3. GDPR / ЗРУ-547

`docs/PRIVACY.md` и работающий процесс:

```
REQUESTED → IDENTITY_VERIFIED → LEGAL_RETENTION_CHECK
→ ANONYMIZATION → MEDIA_DELETION → AUDIT → COMPLETED
```

- Реестр обработки: какие ПДн, зачем, на каком основании, сколько хранятся, куда передаются.
- Локализация (Q6): подтверди, что ПДн физически не покидают территорию — включая Sentry, логи и бэкапы. Это чаще всего нарушается именно через внешний APM.
- Анонимизация, а не удаление, там, где финансовый ретеншен запрещает удаление: номер заменяется необратимым токеном, сумма и дата сохраняются.
- SLA ответа на запрос — назови конкретный срок из применимого закона.
- Тест: запрос на удаление проходит весь цикл; после него номер не восстановим ни из БД, ни из MinIO, ни из логов, ни из бэкапа новее даты удаления; при этом финансовая отчётность за период не изменилась.

## 6. Отчёт о готовности

Заверши фазу документом `docs/PRODUCTION_READINESS.md`:

1. **Что работает** — со ссылками на подтверждающие артефакты.
2. **Что не работает и почему** — честно. Пункт, закрытый формально, но не проверенный в бою, указывается здесь.
3. **Известные риски** — что вероятнее всего сломается в первый месяц эксплуатации и как это будет обнаружено.
4. **Технический долг** — с оценкой стоимости исправления.
5. **Чего система не умеет** — явные границы. Автономная работа площадки без связи, мультивалютность, что-либо ещё из вынесенного за скоуп.
6. **Условия запуска** — что обязано быть сделано до первой реальной машины на первой реальной площадке.

Этот документ ценнее чек-листа. Чек-лист показывает, что сделано; отчёт показывает, чему можно доверять.
