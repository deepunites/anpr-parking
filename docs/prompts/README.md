# ANPR Parking Platform — Prompt Kit v3.0

Переработанная версия MASTER SPECIFICATION v2.0. Исходный документ был хорошим ТЗ, но плохим промтом: один запрос на 3–6 месяцев работы, внутренние противоречия и ошибки в DDL, которые LLM воспроизвела бы дословно.

Здесь тот же продукт, разложенный на исполнимые фазы с проверяемой приёмкой.

---

## Что изменилось по сравнению с v2.0

| Проблема v2.0 | Решение v3.0 |
|---|---|
| Один промт на весь проект | 10 отдельных промтов, каждый = 1–3 дня работы |
| «no mock» при неизвестных внешних API | §7 CORE: явное правило — порт + адаптер + contract test; fake только в тестах |
| Противоречия разрешались молча | §8 CORE: STOP-протокол, модель обязана остановиться и спросить |
| Баги в DDL уходили в код as-is | Схема помечена как черновик; фаза 2 начинается с её критики |
| DoD как декларация | Gate после каждой фазы: конкретные команды + их вывод |
| Ролевая преамбула на 10 строк | Убрана, заменена проверяемыми инвариантами |
| Несогласованные цифры масштаба | §3 CORE: пересчитано, каждая цифра выводится из соседних |
| `python-jose`, `passlib` | PyJWT + argon2-cffi (см. §6 CORE, обоснование там же) |
| GDPR при работе в UZ | §12 CORE: ЗРУ-547 как основа, GDPR — опция |

## Как пользоваться

### Вариант А — агент с доступом к файлам (Claude Code, Cursor, Codex)

Положи папку в репозиторий как `docs/prompts/` и запускай:

```
Прочитай docs/prompts/00-CORE.md и docs/prompts/PHASE-01-architecture.md.
Выполни фазу 1.
```

### Вариант Б — чат без файлов

Вставляй в одно сообщение: содержимое `00-CORE.md`, затем содержимое нужного `PHASE-XX`.
`00-CORE.md` вставляется заново в каждой новой сессии.

### Порядок

```
PHASE-01  Архитектура + ADR            → gate 1
PHASE-02  БД, миграции, RLS            → gate 2
PHASE-03  Backend core (домен + API)   → gate 3
PHASE-04  Камеры, шлагбаумы, offline   → gate 4
PHASE-05  Платежи и сверка             → gate 5
PHASE-06  Frontend                     → gate 6
PHASE-07  Observability                → gate 7
PHASE-08  Тесты (unit/integration/E2E/failure/load) → gate 8
PHASE-09  Инфраструктура и CI/CD       → gate 9
PHASE-10  Production review            → финал
```

**Фазу нельзя начинать, пока не пройден gate предыдущей.** Gate — это вывод команд в терминале, а не заявление модели о готовности.

## Что делать перед стартом

1. Открой `00-CORE.md` §12 «Открытые вопросы».
2. Ответь на 9 вопросов (у каждого есть дефолт — можно оставить дефолт, но осознанно).
3. Впиши ответы прямо в `00-CORE.md`, заменив блок `DEFAULT:` на `ANSWER:`.

Без этого шага модель примет решения за тебя — и они попадут в схему БД, откуда их дорого выковыривать.

## Оценка трудоёмкости

Реалистично для одного разработчика с LLM-ассистентом:

| Фаза | Срок | Основной риск |
|---|---|---|
| 1 | 1–2 дня | Недоопределённые границы контекстов |
| 2 | 3–5 дней | RLS + партиционирование + уникальность идемпотентности |
| 3 | 3–4 недели | Саги, транзакционные границы |
| 4 | 1–2 недели | Реальный протокол камер и шлагбаумов |
| 5 | 2–3 недели | Интеграция провайдера, сверка |
| 6 | 3–4 недели | Объём экранов |
| 7 | 1 неделя | Кардинальность метрик |
| 8 | 2–3 недели | Failure-тесты, k6 |
| 9 | 2–3 недели | HA PostgreSQL, PITR, drill |
| 10 | 1 неделя | — |

**Итого: 4–6 месяцев.** Если срок меньше — режь MVP по §11 CORE, а не качество.
