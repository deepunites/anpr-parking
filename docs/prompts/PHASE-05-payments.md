# PHASE 05 — Платежи, возвраты, сверка

**Предусловие:** gate фазы 4 пройден.
**Это самая опасная фаза проекта.** Ошибка здесь стоит денег и не всегда обнаруживается сразу.

---

## 1. Принципы

1. **Никогда не мутируй завершённый платёж** (I-6). Любая коррекция — новая компенсирующая запись со ссылкой на исходную.
2. **Провайдер — источник истины по факту оплаты, мы — по обязательству.** Расхождение разрешается в пользу провайдера и попадает в очередь сверки, а не правится молча.
3. **Идемпотентность обязательна на каждой границе.** Двойное списание — недопустимо; двойное открытие шлагбаума — терпимо.
4. **Ретрай неидемпотентной операции запрещён.** Если не знаешь, прошёл ли платёж, — не повторяй, а спрашивай статус.
5. **Сумма считается на бэкенде.** Сумма, пришедшая от клиента, используется только для сверки с посчитанной; расхождение — отказ.

---

## 2. Модель

```
Payment              обязательство: сколько и за что
PaymentAttempt       каждая попытка провести через провайдера
Refund               возврат, всегда со ссылкой на Payment
PaymentReconciliation  результат сверки за период
ReconciliationDiscrepancy  конкретное расхождение, требующее решения
```

`PaymentAttempt` хранит: провайдер, `provider_transaction_id`, наш request id, отправленный запрос (без секретов), код и тело ответа, HTTP-статус, код ошибки провайдера, latency, timestamps, номер попытки. Это то, что спасёт при разборе спорной транзакции через полгода.

## 3. Способы оплаты

### CASH

Проводится кассиром. Требует: аутентифицированного пользователя с разрешением `payment:create_cash`, привязки к площадке, `reason` при нестандартной сумме, записи в аудит с `operator_id`.

Отдельно: **смены кассиров**. Наличные без учёта смены не сверяются. Спроектируй `cashier_shift` (открытие, закрытие, начальный остаток, инкассация, расхождение факт/расчёт) — без этого наличная выручка неаудируема. Если решаешь не делать — оформи ADR с обоснованием и последствиями.

### CARD / ONLINE

Порт:

```python
class PaymentGateway(Protocol):
    async def create(self, req: PaymentRequest) -> PaymentIntent: ...
    async def status(self, provider_tx_id: str) -> PaymentStatusResult: ...
    async def refund(self, req: RefundRequest) -> RefundResult: ...
```

Адаптеры по дефолту Q1 (Payme, Click). Каждый адаптер обязан:

- Использовать `idempotency_key`, устойчивый между попытками.
- Проверять подпись входящего вебхука до любой обработки.
- Быть идемпотентным по вебхуку: тот же вебхук дважды = один эффект.
- Иметь таймаут, circuit breaker, метрики, трейсинг.
- Никогда не логировать секреты и полные реквизиты.

**Вебхук:**

```
POST /api/v1/payments/webhook/{provider}
```

Порядок: проверка подписи → проверка времени (защита от replay) → поиск платежа по `provider_transaction_id` → проверка суммы и валюты → применение → ответ. **Быстрый ответ 200 и асинхронная обработка** — провайдеры имеют короткие таймауты и ретраят.

Вебхук может прийти раньше, чем мы сохранили `provider_transaction_id`. Это штатная гонка. Решение: запись «осиротевшего» вебхука в отдельную таблицу и повторное применение при появлении платежа. Не теряй его.

### SUBSCRIPTION / VIP

Платёж создаётся со статусом `PAID`, суммой 0, методом `SUBSCRIPTION`/`VIP` и ссылкой на основание. Это нужно для отчётности: бесплатный проезд обязан быть виден в отчёте как использование льготы, а не как отсутствие платежа.

## 4. Возвраты

- Только со ссылкой на `Payment` в статусе `PAID`.
- Сумма возврата ≤ сумма платежа минус уже возвращённое. Проверка в БД, не только в коде.
- Частичные возвраты допустимы.
- Требуют разрешения `payment:refund`, `reason`, аудита.
- Возврат наличных — отдельная ветка с привязкой к смене.
- Возврат не мутирует исходный платёж; статус `REFUNDED` выставляется производно, когда сумма возвратов равна сумме платежа.

## 5. Сверка

Celery-задача, ежедневно + по требованию.

```
за период:
  выгрузить наши PAID/REFUNDED
  выгрузить реестр провайдера
  сопоставить по provider_transaction_id
```

Классы расхождений:

| Класс | Смысл | Действие по умолчанию |
|---|---|---|
| `MISSING_LOCAL` | есть у провайдера, нет у нас | создать платёж, закрыть сессию, алерт |
| `MISSING_REMOTE` | есть у нас PAID, нет у провайдера | пометить под расследование, **не** отменять автоматически |
| `AMOUNT_MISMATCH` | суммы разошлись | очередь, ручное решение |
| `STATUS_MISMATCH` | статусы разошлись | подтянуть статус провайдера, аудит |
| `DUPLICATE_REMOTE` | два платежа провайдера на одну сессию | очередь возврата, алерт высокого приоритета |

Каждое расхождение — строка в `ReconciliationDiscrepancy` со статусом (`OPEN`, `RESOLVED`, `WRITTEN_OFF`), исполнителем и решением. Метрика `reconciliation_discrepancies_open` с алертом при росте.

Отчёт сверки сохраняется целиком, не только расхождения — иначе невозможно доказать, что сверка проводилась.

## 6. Интеграция с EXIT-сагой

Точки отказа, которые нужно покрыть явно:

- Провайдер не ответил в таймаут → **не** ретраить создание; запросить статус по нашему idempotency key; если статус неизвестен — сага в `PAYMENT_PENDING_VERIFICATION`, машина не выпускается, оператор получает уведомление.
- Платёж прошёл, шлагбаум не открылся → платёж остаётся, сага в `MANUAL_REVIEW`, алерт. Деньги не возвращаются автоматически: обязательство исполнено, проблема механическая.
- Водитель уехал через соседний выезд после оплаты → сессия закрывается по платежу, `exit_time` = время платежа, помечается как `EXIT_INFERRED`.
- Оплата прошла дважды (двойной вебхук с разными `provider_transaction_id`) → второй платёж автоматически в очередь возврата.

Каждый случай — тест.
