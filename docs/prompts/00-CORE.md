## 1. Продукт

Multi-tenant SaaS-платформа автоматизированной парковки с ANPR-распознаванием номеров. Оператор паркингов (tenant) управляет несколькими площадками; въезд и выезд автоматические, оплата — наличные, карта, онлайн, абонемент.

Основной поток:

```
ANPR-камера → Camera API → аутентификация → валидация → идемпотентность
→ доменная логика → сессия → тариф → оплата → шлагбаум → аудит → аналитика
```

## 2. Приоритет требований

При конфликте выигрывает то, что выше:

1. **Корректность денег и доступа.** Ошибка в сумме или открытый чужому шлагбаум — недопустимы.
2. **Сохранность событий.** Принятое событие не теряется.
3. **Изоляция tenant.** Утечка между организациями — фатальна.
4. **Аудируемость.** Любое действие восстановимо постфактум.
5. **Доступность.**
6. **Latency.**
7. **Стоимость.**
8. **Функциональная полнота.**

Не жертвуй пунктом 1–3 ради 5–8. Если кажется, что приходится — это случай для STOP-протокола (§8).

## 3. Масштаб (цифры согласованы между собой — не меняй одну без пересчёта остальных)

```
Tenants:                        100
Parking lots:                   1 000 (в среднем 10 на tenant)
Камер на lot:                   до 30, в среднем 6
Камер всего:                    ~6 000 в среднем, 30 000 потолок
Мест на площадку:               до 2 000
```

**Камеры — HTTP-клиенты, а не постоянные соединения.** Никакого пула на 30 000 сокетов не нужно. Это меняет архитектуру: масштабируемся по RPS, а не по числу соединений.

```
Parking sessions:               1 000 000 / сутки
ANPR events (2 на сессию + брак/дубли ≈ 25%):
                                2 500 000 / сутки
                                ≈ 29 RPS среднее
                                ≈ 200 RPS пик (коэф. 7 — утренний и вечерний час пик)
                                ≈ 400 RPS абсолютный пик (проектный запас x2)

Heartbeat камер: интервал 300 с → 30 000 / 300 = 100 RPS
```

**Следствие, которое обязано попасть в архитектуру:** heartbeat создаёт трафик того же порядка, что и полезные события. Heartbeat **не пишется в PostgreSQL синхронно** — он идёт в Redis (`HSET` + TTL), а в PG сбрасывается батчем раз в 60 с. Иначе 100 RPS бессмысленных UPDATE на `camera` съедят WAL и autovacuum.

```
Записи EventLog + AuditLog + PaymentAttempt: ~10 000 000 / сутки
Операторов на площадку:         до 50
Операторов глобально:           до 1 000
```

## 4. SLO

| Операция | SLI | SLO | Порог алерта |
|---|---|---|---|
| `POST /camera/events` | p95 latency | < 150 ms | p95 > 250 ms 5 мин |
| `POST /camera/events` | доля 5xx | < 0.1 % | > 0.5 % 5 мин |
| EXIT end-to-end (событие → шлагбаум открыт, без оплаты) | p95 | < 2 s | > 4 s 5 мин |
| Открытие шлагбаума | success rate | > 99.5 % | < 98 % 10 мин |
| Подтверждение платежа | p95 | < 5 s | > 10 s 5 мин |
| API в целом | доступность | 99.9 % / мес | error budget 50 % израсходован |

```
Availability: 99.9 %  → 43 минуты недоступности в месяц
RTO: ≤ 15 минут
RPO: ≤ 5 минут для аналитических данных
RPO: 0 для принятых ANPR-событий и платежей
```

**Важно — здесь v2.0 противоречила сама себе.** «RPO ≤ 5 мин» и «события не теряются» несовместимы при асинхронной репликации. Разрешение:

- Синхронная реплика (`synchronous_commit = remote_apply`, `synchronous_standby_names` с одним standby) для транзакций, записывающих `anpr_event`, `parking_session`, `payment`, `outbox`. RPO = 0, цена — +2–5 ms на коммит.
- Асинхронная репликация и PITR (RPO ≤ 5 мин) для `event_log`, `audit_log`, аналитики.
- Разделение — через два пула соединений с разным `synchronous_commit`, выставляемым на уровне сессии.

## 5. Инварианты

Это ядро документа. Каждый инвариант обязан иметь: (а) механизм принуждения, (б) автотест, который падает при его нарушении. Фаза не принимается без тестов на затронутые ею инварианты.

| # | Инвариант | Принуждение |
|---|---|---|
| I-1 | В паре (lot, vehicle) не может быть больше одной сессии в статусе ACTIVE | partial unique index в PG |
| I-2 | Ни один запрос не возвращает и не пишет строки чужого tenant | RLS + отдельная роль приложения + тест на каждую таблицу |
| I-3 | Повторная доставка camera-события не создаёт вторую сессию и не открывает шлагбаум второй раз | unique на idempotency_key + возврат исходного результата |
| I-4 | Событие, на которое API вернул 2xx, доходит до PostgreSQL или до DLQ — но не исчезает | запись в PG в той же транзакции либо `XADD` в Redis Stream до ответа |
| I-5 | Ни один integration event не публикуется раньше коммита транзакции, его породившей | Outbox, публикация только из `outbox` таблицы |
| I-6 | Payment в статусе PAID/REFUNDED никогда не мутируется | триггер PG, запрещающий UPDATE терминальных статусов + компенсирующие записи |
| I-7 | Расчёт стоимости детерминирован: одни и те же (entry, exit, tariff_version, access_type, discount) всегда дают один amount | pure-функция без I/O + property-based тест |
| I-8 | При активном попадании в blacklist шлагбаум не открывается автоматически | явная ветка в авторизации + тест |
| I-9 | Открытая транзакция PostgreSQL никогда не ждёт внешний HTTP | архитектурный тест: HTTP-клиенты запрещены внутри UoW-скоупа |
| I-10 | Номер в открытом виде не хранится ни в одной колонке, не пишется в лог, метрику, трейс и Sentry | отсутствие plaintext-колонки + log-фильтр + тест на выхлоп логгера |
| I-11 | AuditLog доступен только на INSERT и SELECT | GRANT без UPDATE/DELETE для роли приложения |
| I-12 | Периоды действия версий одного тарифного плана не пересекаются | EXCLUDE USING gist |
| I-13 | Деньги — целые в минорных единицах на всём пути: БД → домен → API → UI | тип `Money` без `__float__`, запрет float в схемах Pydantic, lint-правило |
| I-14 | Приложение не стартует, если отсутствует обязательный секрет или конфиг | валидация на старте, `sys.exit(1)` |
| I-15 | Любое ручное действие оператора содержит user_id, reason и запись в AuditLog | обязательный параметр `reason` в команде + тест |
| I-16 | Ручная коррекция номера не затирает исходное распознавание | отдельные колонки raw / corrected |

**Замены относительно исходного ТЗ и их причина:**

- `python-jose` → **PyJWT**. python-jose фактически не поддерживается, имеет историю CVE в разборе алгоритмов. Нужен JWT, а не весь JOSE.
- `passlib[argon2]` → **argon2-cffi напрямую**. Последний релиз passlib — 2020, он ломается на bcrypt 4.x. Прослойка не даёт ничего.
- `pybreaker` → **purgatory**. pybreaker синхронный; на async-коде даёт ложное чувство защиты.
- `factory-boy` → **polyfactory** (фаза 8). factory-boy рассчитан на sync ORM, polyfactory работает с Pydantic и dataclass.

## 7. Что считается mock и что разрешено

В исходном ТЗ был неразрешимый конфликт: запрет на mock при неизвестных внешних API. Разрешение:

**Запрещено:**

- `raise NotImplementedError`, `pass  # TODO`, `...` в теле функции продакшн-кода
- Заглушки, возвращающие константу, в продакшн-пути
- Комментарии `TODO`, `FIXME`, «реализовать позже», «пример»
- Вымышленные URL, ключи, токены в коде и конфигах

**Разрешено и требуется:**

- Порт (Protocol) + конкретная реализация адаптера по **документированному** протоколу внешней системы.
- Если протокол не определён (см. §12) — адаптер реализуется по протоколу из дефолта, помечается в `ARCHITECTURE.md` как «требует подтверждения», и покрывается contract-тестом.
- Fake-реализация порта — **только** в `tests/`, никогда в `src/`.
- Feature flag, отключающий незавершённую интеграцию, — допустим, если флаг валидируется на старте и выключенное состояние даёт понятную ошибку, а не тихий no-op.

## 8. STOP-протокол

Если ты обнаружил:

- противоречие между двумя требованиями,
- требование, невыполнимое на выбранном стеке,
- необходимость выбрать то, что повлияет на схему БД или контракт API и не задано явно,

то **остановись**. Не выбирай молча. Выведи:

```
STOP: <одна строка — суть конфликта>
Где: <раздел/файл A> vs <раздел/файл B>
Вариант 1: <решение> — цена: <что теряем>
Вариант 2: <решение> — цена: <что теряем>
Рекомендую: <номер> — потому что <одна причина>
```

и жди ответа. Исключение: если ответа нет и работа идёт автономно — возьми рекомендованный вариант, запиши его в `docs/ASSUMPTIONS.md` строкой `[ДОПУЩЕНИЕ] <решение> — требует подтверждения`, и продолжай.

## 9. Формат вывода

Каждая фаза начинается с **ADR-блока**, не с кода. Для каждого решения:

```
### ADR-NN: <решение одной строкой>
Контекст:      ≤ 3 предложения
Решение:       ≤ 3 предложения
Отвергнуто:    2 альтернативы + одна причина отказа на каждую
Последствия:   что становится проще, что — дороже
Риск:          что сломается, если решение окажется неверным, и как это обнаружить
```

Лимит: **200 слов на ADR**. Прозы между ADR быть не должно.

Далее — код. Правила:

- Python 3.12, полная типизация, `mypy --strict` без `# type: ignore` (исключения — только для чужих библиотек без стабов, с комментарием-причиной).
- Docstring на публичных функциях: что делает, что бросает. Не пересказывай сигнатуру.
- Структурированное логирование на границах: вход в use case, внешний вызов, ошибка.
- Никогда не выводи содержимое файла целиком, если поменялись 5 строк — выводи diff.

## 12. Открытые вопросы

Ответы даны 2026-09-19 (фаза 1). Пункты с пометкой [ДОПУЩЕНИЕ A-nn] требуют подтверждения — см. docs/ASSUMPTIONS.md. Если оставляешь дефолт — оставь его осознанно, он уйдёт в схему БД.

**Q1. Платёжный провайдер.**
ANSWER: Payme + Click через порт `PaymentGateway`; онлайн-оплата по redirect/QR, вебхук подтверждения, идемпотентность по `provider_transaction_id`. Адаптеры пишутся по публичной документации провайдеров (Payme Merchant API, Click SHOP API), помечаются «требует подтверждения» и покрываются contract-тестами; мерчант-аккаунтов нет — интеграция за feature-flag с валидацией на старте. **Наличные (CASH) — обязательный и основной способ оплаты с MVP**, не зависят от провайдеров; смены кассиров проектируются в фазе 5.

**Q2. Протокол камер.**
ANSWER: Push-модель. Между камерой и нормализованным Camera API стоит vendor-адаптер на нашей стороне: `POST /api/v1/camera/vendor/{hikvision|dahua}` принимает родной формат с изображением, кладёт изображение в MinIO, формирует `image_object_key` и вызывает тот же ingest-путь, что и нормализованный `POST /api/v1/camera/events`. Нормализованный эндпоинт — контракт для тестов, k6 и камер/шлюзов с настраиваемым телом. Presigned PUT — для UI и агентов, не для камер. Pull через ISAPI/ONVIF не реализуется. [ДОПУЩЕНИЕ A-02]

**Q3. Протокол шлагбаума.**
ANSWER: Оба драйвера за портом `BarrierDriver`: `ModbusTcpDriver` (сухой контакт через IP-релей) — основной рабочий; `HttpRestDriver` (`POST /open`, `POST /close`, `GET /status`, Bearer) — по протоколу дефолта, «требует подтверждения». Драйвер выбирается полем `barrier.driver`. [ДОПУЩЕНИЕ A-03]

**Q4. Greenfield или есть код?**
ANSWER: Greenfield, пустая папка проекта. Система контроля версий — на стороне владельца проекта (git-операции в фазах не выполняются).

**Q5. Деплой.**
ANSWER: Self-hosted Kubernetes на серверах в UZ, MinIO вместо S3, PostgreSQL под Patroni. Рабочее допущение: слой под кластером — виртуализация с API (Proxmox); Terraform управляет ВМ, сетью, DNS, TLS. Если окажется bare metal — в фазе 9 Terraform заменяется Ansible; схема и код не меняются. [ДОПУЩЕНИЕ A-04]

**Q6. Юрисдикция ПДн.**
ANSWER: Узбекистан, ЗРУ-547 «О персональных данных»; локализация — жёсткое требование. Следствия: Sentry self-hosted внутри контура, Prometheus/Loki/бэкапы — на территории UZ, внешние SaaS с ПДн не используются. Номер ТС трактуется как ПДн. GDPR-механики (право на удаление, минимизация, DPIA) — как надмножество.

**Q7. Оффлайн-автономность площадки.**
ANSWER: Автономности нет. При обрыве связи с ЦОД площадка переходит в ручной режим (шлагбаум — кнопкой охранника), сессии таких машин закрываются оператором постфактум (orphan/коррекция). Оффлайн-режим §27 покрывает только недоступность PostgreSQL при живом API. Бизнес-риск зафиксирован как [ДОПУЩЕНИЕ A-01] и требует подтверждения заказчиком.

**Q8. Валюта и мультивалютность.**
ANSWER: Только UZS, тийин в BIGINT (1 UZS = 100 тийин); `currency CHAR(3)` в схеме предусмотрен, конвертация не реализуется.

**Q9. Кто держит ключи шифрования номеров.**
ANSWER: Per-tenant DEK (AES-256-GCM) и HMAC-ключ, обёрнутые KEK в HashiCorp Vault Transit; в БД — только ссылка на ключ и версия. Vault не на горячем пути: ключи разворачиваются при старте процесса и кешируются в памяти с версией; Vault вызывается при старте, ротации и создании tenant. Ротация — фоновая перешифровка с версионированием, поиск по хешам обеих версий в переходный период. [ДОПУЩЕНИЕ A-05]

## 13. Gate — как принимается фаза

Фаза считается завершённой, только когда ты вывел **фактический вывод команд**, а не утверждение об их успехе.

Общий gate для всех фаз с кодом:

```bash
uv run ruff check . && uv run ruff format --check .
uv run mypy --strict src/
uv run pytest -q
uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head
```

Плюс частный gate фазы, описанный в её файле.

Если команда падает — фаза не завершена. Не переходи дальше, не пиши «осталось поправить мелочи». Чини.
