## 1. Что произвести

### 1.1 C4

**Context.** Внешние акторы: ANPR-камера, контроллер шлагбаума, оператор, кассир, администратор tenant, платёжный провайдер, Telegram, водитель. Для каждого — что он посылает и что получает.

**Container.** Минимум: API (FastAPI), Camera Ingest (может быть тем же контейнером — обоснуй, почему да или нет), Outbox Publisher, Stream Consumer, Celery workers (разделённые по очередям), WebSocket Gateway, PostgreSQL (primary + sync standby + async standby), Redis, MinIO, Frontend.

Для каждого контейнера: назначение, протоколы входа и выхода, состояние (stateless или нет), как масштабируется, что произойдёт при его падении.

**Component** — для трёх контейнеров: API, Stream Consumer, Outbox Publisher.

Формат: Mermaid в `docs/ARCHITECTURE.md`. Не ASCII-арт.

### 1.2 Bounded contexts

15 контекстов из исходного ТЗ — гипотеза, а не данность. Проверь её и обоснуй финальный список. Проверка: контекст существует, если у него есть собственный язык и собственные инварианты. `Tenant Management` и `Identity & Access`, вероятно, один контекст. `Analytics` и `Reporting` — вероятно, тоже.

Для каждого финального контекста:

```
Назначение (1 строка)
Агрегаты и их корни
Границы транзакции (что меняется атомарно)
Value objects
Domain events (внутренние)
Integration events (публикуемые наружу) + версия контракта
Зависимости: от кого потребляет события, кому публикует
Владение таблицами
```

Обязательно — **context map** с типом связи (Customer/Supplier, Conformist, ACL, Shared Kernel).

### 1.3 Ключевые решения, которые нужно принять в этой фазе

Не откладывай ни одно из них. Каждое — отдельный ADR.

1. **Монолит или сервисы.** Рекомендуемая отправная точка — модульный монолит с жёсткими границами модулей и отдельно масштабируемыми воркерами. Обоснуй выбор через нагрузку из §3 CORE и размер команды.
2. **Разделение на пулы соединений** под требование RPO из §4 CORE: какие транзакции идут через `synchronous_commit = remote_apply`, какие — через `off`.
3. **Где живёт авторизация доступа** (blacklist / whitelist / VIP / subscription): это один контекст `Access Control` или четыре сущности внутри `Parking Session`? Решение влияет на число запросов в горячем пути EXIT.
4. **Кеш авторизации.** При 200 RPS каждый EXIT делает 4 проверки списков. Проектируется ли Redis-кеш списков, и как обеспечивается инвалидация при добавлении в blacklist (требование: попадание в blacklist вступает в силу не позже чем через N секунд — назови N и обоснуй).
5. **Где считается occupancy.** Агрегат, материализованное представление или счётчик в Redis. Как разрешается расхождение между `ParkingSpot.status` и числом активных сессий.
6. **Кто владеет `Vehicle`** — отдельный контекст или часть `Parking Session`.
7. **Транспорт integration events.** Outbox → что? Redis Streams, PostgreSQL LISTEN/NOTIFY, брокер. Обоснуй через требование «не терять» и через количество потребителей.

### 1.4 Sequence diagrams (Mermaid)

Обязательно:

1. ENTRY, happy path — от HTTP-запроса камеры до `ENTRY_CONFIRMED`, с явными границами транзакций.
2. EXIT с оплатой — вся сага, с точками персистентности состояния.
3. EXIT по абонементу — без оплаты.
4. Дубликат ANPR-события — как возвращается тот же результат.
5. Оффлайн: PostgreSQL недоступен → Redis Stream → восстановление → консьюмер.
6. Отказ шлагбаума после успешного платежа — компенсация или ручной сценарий.
7. Ротация ключа камеры без простоя.

На каждой диаграмме отметь, где транзакция БД открыта и где закрыта. Инвариант I-9 должен быть визуально проверяем.

### 1.5 State machines

`ParkingSession`, `Payment`, `Barrier`, `ExitSaga`, `CameraHealth`.

Для каждой: состояния, разрешённые переходы, событие-триггер, побочный эффект перехода, терминальные состояния, таймауты, что происходит при падении процесса в каждом состоянии.

Отдельно для `ExitSaga`: для каждого шага — компенсирующее действие или обоснование, почему компенсация невозможна и нужен ручной сценарий.

### 1.6 Failure matrix

Таблица: отказавший компонент × что деградирует × что продолжает работать × как обнаруживается × автоматическое восстановление × ручное действие.

Минимум: PostgreSQL primary, PostgreSQL sync standby, Redis, MinIO, Celery, платёжный провайдер, шлагбаум, камера, сеть между API и БД, полная потеря зоны.

### 1.7 Модель безопасности

- Границы доверия на диаграмме.
- Для каждой из трёх групп API (public / camera / admin) — кто аутентифицируется, чем, что может.
- Схема работы с ключами: per-tenant DEK, KEK, Vault Transit, ротация, что произойдёт при компрометации одного tenant-ключа.
- Полная threat-модель — **фаза 10**. Здесь только каркас.

## 3. Точки, где почти наверняка потребуется STOP

Проверь эти места. Если решение не выводится из `00-CORE.md` — применяй §8 STOP-протокол.

- Один ли `Vehicle` на tenant или на площадку (влияет на I-1).
- Считать ли сессию активной, если машина уехала мимо камеры (orphan): по таймауту, вручную или обоими способами.
- Что делать, если EXIT-событие пришло, а активной сессии нет (машина въехала до запуска системы).
- Что делать при двух EXIT-событиях по одной сессии с разных камер.
- Открывать ли шлагбаум при недоступности платёжного провайдера и предоплаченном абонементе.
