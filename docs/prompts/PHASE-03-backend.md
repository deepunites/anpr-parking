```
      access/          # blacklist, whitelist, VIP, абонементы

      v1/
      deps.py
      errors.py
      middleware/
    workers/
      outbox_publisher.py
      stream_consumer.py
      celery_app.py
  tests/
```

Внутри каждого модуля:

```
domain/         # сущности, VO, доменные сервисы, события. Импортов из infrastructure — ноль.
application/    # use cases, порты, DTO, обработчики команд
infrastructure/ # репозитории, адаптеры, ORM-модели
```

**Правило импортов, проверяемое автотестом:** `domain` не импортирует `application` и `infrastructure`. `application` не импортирует `infrastructure`. Модуль A не импортирует `modules.B.infrastructure` и `modules.B.domain` — только `modules.B.application.contracts`. Напиши архитектурный тест (обход AST по `src/`), который падает при нарушении. Это единственная защита от расползания границ.

## Подфаза 3.1 — Фундамент

### Money (I-13)

```python
@dataclass(frozen=True, slots=True)
class Money:
    minor: int        # тийины
    currency: Currency
```

Требования: сложение и вычитание только в одной валюте; умножение на `Fraction` или `Decimal` с **явным** режимом округления, не на `float`; отсутствие `__float__` и `__int__`; сериализация в API как `{"minor": 1500000, "currency": "UZS", "formatted": "15 000,00 сум"}` — форматирование на бэкенде, чтобы фронт не занимался арифметикой. Property-based тест на ассоциативность сложения и на отсутствие потери копеек при делении суммы.

### PlateNumber

VO с нормализацией. Правила нормализации выведи из формата узбекских номеров и покрой тестами. Минимум: приведение регистра, отбрасывание разделителей, транслитерация кириллических омоглифов (А, В, Е, К, М, Н, О, Р, С, Т, У, Х) в латиницу. `__repr__` и `__str__` обязаны маскировать значение (`01A***AA`) — это защита I-10 от случайного попадания в лог.

### Конфиг

`pydantic-settings`, валидация на старте, `sys.exit(1)` при отсутствии обязательного. Отдельные классы для dev/staging/prod; в prod запрещены дефолты для секретов, `DEBUG=True` и `*` в CORS — запрет на уровне валидатора, не соглашения. Тест: запуск с пустым окружением падает с понятным сообщением (I-14).

### Логи

`structlog`, JSON. Процессор-редактор, вырезающий из любого события ключи и значения, похожие на номер, JWT, ключ, пароль, токен. **Тест: пропусти через логгер объект, содержащий номер и JWT, и проверь, что в выводе их нет** (I-10).

`contextvars` для `correlation_id`, `tenant_id`, `trace_id` — автоматически во всех записях.

### Unit of Work

Async, на `AsyncSession`. Один UoW = одна транзакция. Метод `collect_events()` собирает доменные события агрегатов и пишет их в `outbox` **в той же транзакции** (I-5).

**Защита I-9:** внутри активного UoW запрещены HTTP-вызовы. Реализуй через `contextvar` — `httpx`-транспорт проверяет флаг и бросает `TransactionBoundaryViolation`. Тест обязателен.

### Ошибки

Иерархия: `DomainError` → `ConflictError`, `NotFoundError`, `ValidationError`, `AuthorizationError`, `ExternalServiceError`. Таблица «класс ошибки → HTTP-код → код в ответе». Хендлер FastAPI, формирующий `{"error": {"code", "message", "correlation_id"}}`. Stack trace клиенту не уходит никогда; в лог — уходит целиком.

**Gate 3.1:** тесты на Money, PlateNumber, редактор логов, валидацию конфига, архитектурный тест импортов, тест на запрет HTTP внутри UoW. Все зелёные, вывод вставлен.

## Подфаза 3.2 — Identity, RBAC, tenancy

### Аутентификация

- Пароли: `argon2-cffi`, параметры — не дефолтные, обоснуй выбор `time_cost`, `memory_cost`, `parallelism` через целевое время хеширования (100–250 мс) и измерь его.
- JWT: `PyJWT`, RS256 или EdDSA (обоснуй), access 15 мин, refresh 7 дней.
- Claims: `sub`, `tenant_id`, `role`, `jti`, `iat`, `exp`, `token_version`. Список permissions в токен **не** кладётся — он разворачивается из роли на бэкенде, иначе изменение прав не вступит в силу до истечения токена.
- Refresh: ротация при каждом использовании, семейство токенов, **детекция повторного использования** — при предъявлении уже использованного refresh отзывается всё семейство и пишется алерт. Это обязательный пункт, не опциональный.
- Брутфорс: экспоненциальная задержка по паре (username, IP) и отдельно по IP, блокировка после N попыток, запись в аудит. Ответ при неверном пароле и при несуществующем пользователе обязан быть неразличим по коду, тексту **и по времени**.

### RBAC

Разрешения — перечисление вида `sessions:read`, `barrier:open`, `payment:refund`, `tariff:write`. Матрица роль → разрешения в коде, не в БД (меняется вместе с кодом, ревьюится в PR).

Проверка — зависимость FastAPI `require(Permission.X)`. Дополнительно — скоуп площадки: оператор с `lot_id` видит только свою площадку. Скоуп применяется **в репозитории**, не в роуте.

Тест: для каждого эндпоинта и каждой роли проверь ожидаемый код ответа. Таблица `(endpoint, role) → status` генерируется из OpenAPI, чтобы новый эндпоинт без теста нельзя было добавить.

**Gate 3.2:** контрактные тесты RBAC для всех существующих эндпоинтов; тест детекции reuse refresh-токена; тест, что изменение роли пользователя действует немедленно; тест изоляции tenant на уровне API (пользователь A не получает объект tenant B, код 404, не 403 — чтобы не подтверждать существование).

## Подфаза 3.3 — Tariff engine

Чистая функция без I/O:

```python
def calculate(
    entry: datetime,
    exit: datetime,
    rules: TariffRules,
    access: AccessDecision,
    calendar: HolidayCalendar,
    tz: ZoneInfo,
) -> TariffCalculation
```

Возвращает `amount: Money`, `billing_minutes: int`, `applied_rules: list[str]`, `breakdown: list[BreakdownLine]`, `tariff_plan_version_id`.

Поддержать: грейс-период, цена первого часа, почасовая, дневной максимум, ночной тариф с окном через полночь, режим округления (вверх / вниз / к ближайшему, шаг конфигурируем), выходные, праздники, VIP (бесплатно), абонемент (бесплатно в пределах срока), скидка whitelist в процентах.

Обязательные тесты:

- Сессия ровно в грейс-период и на секунду дольше.
- Пересечение полуночи, в том числе с ночным тарифом.
- Переход на другой день недели в середине сессии.
- Праздник, начавшийся в середине сессии.
- Сессия длиной 7 суток при дневном максимуме.
- Сессия нулевой длины и отрицательной (exit < entry) — должна бросать, не считать.
- Property-based (hypothesis): для любых входов результат детерминирован, неотрицателен, монотонно неубывающ по длительности при фиксированных правилах (I-7).
- Скидка 33 % на 1000 тийин — проверь, что копейка не теряется и не создаётся.

`breakdown` сохраняется в `payment.calculation_snapshot`. Изменение тарифа задним числом не меняет исторические платежи — тест на это тоже.

**Gate 3.3:** покрытие модуля tariff ≥ 95 %, все перечисленные случаи зелёные.

## Подфаза 3.4 — Access control

Единая точка: `AccessResolver.resolve(tenant_id, lot_id, plate_hash, at) -> AccessDecision`.

`AccessDecision` содержит: `kind` (NORMAL, VIP, SUBSCRIPTION, WHITELIST, BLACKLIST), `discount_percent`, `source_id`, `reason`.

Требования:

- Один запрос в БД на всё разрешение, не четыре. Обоснуй выбор: UNION ALL по четырём таблицам либо отдельная денормализованная таблица правил доступа, обновляемая через outbox. Замерь оба варианта на 1 млн строк.
- Приоритет: BLACKLIST выигрывает у всего остального всегда.
- Кеш в Redis с TTL. Инвалидация при добавлении в blacklist — немедленная (publish в канал + локальный кеш процесса с коротким TTL). Назови и обоснуй максимальную задержку вступления в силу.
- При недоступности Redis — деградация к прямому запросу в БД, не отказ.

Тест: добавление в blacklist вступает в силу не позже заявленного срока при прогретом кеше.

**Gate 3.4:** тест приоритета, тест инвалидации, тест деградации без Redis, бенчмарк разрешения доступа (p95 < 10 мс на прогретом кеше).

## Подфаза 3.5 — Сессии, ENTRY, EXIT-сага, outbox

### ENTRY

Одна транзакция:

```
резолв vehicle (INSERT ... ON CONFLICT DO UPDATE ... RETURNING)
+ проверка активной сессии
+ создание сессии
+ запись в outbox
```

Гонка двух одновременных ENTRY по одной машине разрешается **уникальным индексом**, а не проверкой «сначала SELECT, потом INSERT». Ловишь `UniqueViolation` → возвращаешь существующую сессию как идемпотентный результат. Тест: 50 параллельных ENTRY по одному номеру → ровно одна сессия, 50 успешных ответов, один и тот же `session_id`.

Открытие шлагбаума — **после** коммита, из обработчика события (I-9).

### EXIT-сага

Персистентное состояние в таблице `exit_saga` (спроектируй её). Шаги из §23 исходного ТЗ. Обязательные свойства:

- Возобновляемость после падения процесса: при старте воркер подбирает саги в незавершённых состояниях старше таймаута.
- Идемпотентность каждого шага.
- Компенсации: для каждого шага либо компенсирующее действие, либо явный переход в `MANUAL_REVIEW`.
- Таймаут на всю сагу и на каждый шаг.
- Отказ шлагбаума **после** успешного платежа не отменяет платёж — деньги уплачены, обязательство исполнено. Сага уходит в состояние, требующее вмешательства оператора, с алертом. Опиши это решение отдельным ADR.

### Outbox publisher

Отдельный процесс. `SELECT ... FOR UPDATE SKIP LOCKED LIMIT N`, публикация, отметка. Гарантия — at-least-once, значит потребители обязаны быть идемпотентны; это записывается в `docs/EVENTS.md` как контракт.

Экспоненциальный бэкофф, после M попыток — `FAILED` и алерт. Метрики `outbox_pending_total`, `outbox_failed_total`, `outbox_publish_lag_seconds`.

Порядок событий одного агрегата сохраняется — обоснуй, как (партиционирование по `aggregate_id` при публикации либо однопоточная публикация на агрегат).

### Реестр событий

`docs/EVENTS.md`: для каждого integration event — имя с версией, JSON Schema, продюсер, потребители, гарантии, правила эволюции. Схемы валидируются в тесте при публикации.

### API

Реализовать эндпоинты §37 исходного ТЗ, кроме камер, шлагбаумов и платежей (фазы 4–5). Для каждого: схема запроса и ответа, коды ошибок, требуемое разрешение, лимит запросов.

Пагинация — **курсорная** на всех коллекциях. OFFSET на миллионе строк запрещён.

OpenAPI 3.1 генерируется из кода, выгружается в `docs/openapi.json` в CI и проверяется на несовместимые изменения (`oasdiff`).
