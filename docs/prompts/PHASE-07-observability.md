# PHASE 07 — Observability

**Предусловие:** gate фазы 6 пройден.

**Критерий приёмки фазы, от которого всё остальное производно:** по метрикам и логам можно ответить на вопрос «почему машина не выехала», не заходя в базу.

---

## 1. Логи

JSON, `structlog`. Обязательные поля:

```
timestamp level service environment version
tenant_id lot_id camera_id user_id session_id
correlation_id trace_id span_id
message error_code duration_ms
```

`correlation_id` создаётся на входе (или берётся из заголовка `X-Correlation-Id`), живёт в `contextvars`, проходит через Celery-задачи, Redis Streams и исходящие HTTP-вызовы. Проверь это тестом на сквозном сценарии: одно camera-событие → все записи логов от API до воркера имеют один `correlation_id`.

**Запрещено в логах** (I-10): номер в открытом виде, JWT, API-ключ, секрет шлагбаума, реквизиты платежа, содержимое `plate_encrypted`, пароль в любом виде.

Уровни: `INFO` — бизнес-события; `WARNING` — деградация с автовосстановлением; `ERROR` — требует внимания; `CRITICAL` — требует немедленного вмешательства. Ожидаемая бизнес-ситуация (дубликат события, машина в blacklist) — это `INFO`, не `ERROR`. Иначе алерты обесценятся за неделю.

Loki: лейблы только низкокардинальные (`service`, `env`, `level`, `tenant_id` — если tenant не больше сотни). `session_id` и `correlation_id` — **в тело, не в лейблы**.

## 2. Метрики

Список из §47 исходного ТЗ — реализуй, но с явной дисциплиной кардинальности.

**Правила лейблов:**

- Никогда: номер, `session_id`, `correlation_id`, `user_id`, произвольный текст ошибки.
- `lot_id` — допустим (1000 значений), но не в сочетании с `camera_id` на одной метрике.
- `camera_id` (30 000 значений) — только на счётчиках, где это оправдано, и никогда на гистограммах. Для здоровья камер используй агрегат по площадке плюс отдельный экспортер со списком проблемных.
- Оцени итоговую кардинальность каждой метрики **до** внедрения и приведи расчёт. Гистограмма с 12 бакетами × 1000 lot × 5 статусов = 60 000 рядов — это уже проблема.

**Бизнес-метрики, без которых не обойтись:**

```
entry_total{lot, result}
exit_total{lot, result}
session_active{lot}
occupancy_ratio{lot}
barrier_command_total{lot, command, result}
payment_total{method, status}
payment_confirm_latency_seconds{method}
revenue_total{method}                      # осторожно: это счётчик, не gauge
camera_event_rejected_total{reason}
camera_clock_skew_seconds{lot}
outbox_pending_total, outbox_failed_total, outbox_publish_lag_seconds
redis_stream_lag, dlq_messages_total
reconciliation_discrepancies_open{kind}
access_decision_total{kind}
manual_correction_total{lot}
```

`revenue_total` в тийинах, целым. Prometheus хранит float64 — до 2^53 тийинов точность сохраняется; отметь это ограничение в `docs/OPERATIONS.md` и не используй метрику как финансовый источник. Финансовая истина — только PostgreSQL.

## 3. Трейсинг

OpenTelemetry, автоинструментация FastAPI, SQLAlchemy, httpx, Redis, Celery.

Ручные спаны на границах доменных операций: `entry.process`, `exit.saga.step`, `tariff.calculate`, `access.resolve`, `barrier.open`, `payment.create`.

Атрибуты спана: `tenant_id`, `lot_id`, `session_id`, `camera_id`, `event_type`. **Номер — никогда.**

Контекст пропагируется через Redis Streams и Celery: `traceparent` кладётся в конверт события и восстанавливается потребителем. Без этого трейс рвётся ровно там, где интереснее всего.

Сэмплирование: 100 % ошибок, 100 % EXIT-саг, 1–5 % успешных ENTRY. Обоснуй частоту через объём и стоимость.

## 4. Дашборды Grafana

Минимум четыре, каждый отвечает на конкретный вопрос:

1. **Operations.** Здоровье площадок: занятость, события, отказы шлагбаумов, оффлайн-камеры. Для оператора и поддержки.
2. **SLO.** Четыре SLI из §4 CORE, расход error budget, тренд.
3. **Pipeline.** Outbox, стримы, DLQ, лаг консьюмеров, лаг репликации, очереди Celery.
4. **Business.** Выручка по способам оплаты, средняя длительность, использование льгот, ручные коррекции, расхождения сверки.

Дашборды — в git как JSON, провижининг через Helm. Кликанье в UI не считается.

## 5. Алерты

Список из §49 исходного ТЗ. У каждого алерта обязательны:

```
severity          critical | warning | info
summary           одна строка, что произошло
description       что это значит для бизнеса
impact            кто и как это почувствует
runbook_url       ссылка на конкретный раздел RUNBOOK.md
for               длительность до срабатывания
```

Алерт без `runbook_url` не принимается.

**Критические (будят человека):** API недоступен, PostgreSQL primary недоступен, лаг синхронной реплики, платежи не проходят, рост DLQ, площадка полностью без камер, бэкап не выполнен, сертификат истекает через 7 дней.

**Warning (ждут рабочего времени):** одна камера оффлайн, отказ одного шлагбаума, рост очереди сверки, лаг outbox, диск 80 %.

Симптомные алерты, а не причинные: «доля успешных выездов упала ниже 98 %» полезнее, чем «CPU 90 %». Причинные оставь для дашбордов.

Проверь на шум: прогони алерты на исторических данных нагрузочного теста фазы 8 и посчитай, сколько сработало бы ложно.

## 6. Sentry

Backend и frontend, release tracking, привязка к коммиту и source maps.

Теги: `tenant_id`, `lot_id`, `camera_id`, `session_id`, `correlation_id`.
`before_send` вырезает номера, токены, ключи и заголовки авторизации. **Тест на `before_send` обязателен** — это последняя линия перед утечкой ПДн во внешний сервис.

Ожидаемые доменные ошибки (дубликат, blacklist, платёж отклонён) в Sentry не отправляются. Иначе он станет нечитаемым.
