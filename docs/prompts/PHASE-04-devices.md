## 1. Camera API

### Эндпоинт

```
POST /api/v1/camera/events
X-Camera-Key: <секрет>
Content-Type: application/json
```

```json
{
  "camera_code": "ENTRY_01",
  "event_type": "ENTRY",
  "plate_number": "01A123AA",
  "confidence": 98,
  "event_time": "2026-09-19T14:20:00+05:00",
  "image_object_key": "tenant/…/frame.jpg",
  "direction": "IN",
  "recognition": {
    "provider": "hikvision",
    "version": "6.2.1",
    "plate_format": "UZ_STANDARD",
    "country_code": "UZ",
    "image_quality": 87,
    "bounding_box": {"x": 120, "y": 340, "w": 210, "h": 60}
  }
}
```

Идентификатор камеры — `camera_code`, а не UUID: камера не знает своего UUID в нашей БД, зато знает символьный код из своей конфигурации. Tenant и площадка определяются по API-ключу, а не из тела запроса. **Значения из тела никогда не расширяют права.**

### Аутентификация

- Ключ из заголовка: первые 16 символов — `key_prefix`, по нему выбирается кандидат из индекса.
- Проверка: HMAC-SHA256 с pepper из Vault, сравнение через `hmac.compare_digest`.
- **Argon2 и bcrypt здесь запрещены** — при 200 RPS это убьёт p95. Обоснование: ключ генерируется системой с 256 битами энтропии, перебор невозможен, растягивание не нужно.
- `last_used_at` не пишется в PostgreSQL на каждом запросе. Redis + флаш батчем.
- Неверный ключ: 401, единый ответ, постоянное время, счётчик метрики, аудит при превышении порога.

### Валидация

Порядок — от дешёвого к дорогому, чтобы мусор отсеивался до обращения к БД:

1. Размер тела ≤ 8 КБ (изображение не передаётся, только ключ объекта).
2. Схема Pydantic, `confidence` 0–100, `event_type` ∈ {ENTRY, EXIT}.
3. Rate limit по ключу камеры (Redis, скользящее окно). Порог — обоснуй через ожидаемую частоту событий с одной камеры.
4. Аутентификация.
5. Камера активна, направление совпадает с `direction` камеры в БД.
6. Клоковый разбег: `|event_time − now| ≤ camera.max_clock_skew_seconds`. Превышение → событие принимается, но помечается и генерирует метрику `camera_clock_skew_seconds`; при систематическом превышении — алерт. **Отклонять нельзя** — иначе сломанные часы камеры остановят площадку.
7. Защита от повтора: `event_time` старше N минут отклоняется как replay. Обоснуй N и его связь с окном идемпотентности из фазы 2.
8. Формат номера, нормализация.
9. `image_object_key` обязан соответствовать шаблону `tenant/{tenant_id}/lot/{lot_id}/camera/{camera_id}/YYYY/MM/DD/{uuid}.jpg`, где tenant, lot и camera совпадают с определёнными по ключу. Любое отклонение — отказ. Это защита от обхода хранилища и от path traversal.

### Политика уверенности

```
confidence >= camera.confidence_min                      → обычная обработка
camera.confidence_review_min <= confidence < min         → MANUAL_REVIEW, шлагбаум не открывается
confidence < camera.confidence_review_min                → отклонить, метрика, изображение сохранить
```

### Идемпотентность

```
idempotency_key = SHA256(
    tenant_id || camera_id || event_type ||
    plate_hash || floor(event_time → секунда)
)
```

Первичный механизм — уникальность в `anpr_idempotency` (фаза 2). Redis — только ускорение, не источник истины. Повторный запрос возвращает **тот же ответ с тем же `session_id`** и кодом 200, не 409.

Тест: 100 параллельных одинаковых запросов → одна сессия, 100 идентичных ответов.

### Ответ

```json
{
  "status": "ENTRY_CONFIRMED",
  "session_id": "…",
  "barrier_command_id": "…",
  "correlation_id": "…",
  "duplicate": false
}
```

Ответ отдаётся **после коммита в БД, но не дожидаясь открытия шлагбаума** — иначе таймаут контроллера станет таймаутом API. Открытие идёт асинхронно; камера узнаёт результат через отдельный запрос статуса или не узнаёт вовсе.

## 2. Heartbeat

```
POST /api/v1/camera/heartbeat
```

100 RPS в целом (§3 CORE). Пишется **только в Redis** (`HSET camera:hb:{id}` + TTL), в PostgreSQL сбрасывается батчем раз в 60 с отдельной задачей. Прямой UPDATE в `camera` на каждом heartbeat запрещён.

Состояния: `ONLINE` (последний heartbeat < 2×интервала), `DEGRADED` (< 5×), `OFFLINE` (иначе или событий нет N минут при ненулевом обычном потоке). Переход в `OFFLINE` публикует integration event и алерт.

Отдельно детектируй «камера жива, но не распознаёт»: heartbeat идёт, событий нет дольше обычного для этого времени суток. Это частый реальный отказ, который простой heartbeat не ловит.

## 3. Шлагбаумы

### Порт

```python
class BarrierDriver(Protocol):
    async def open(self, cmd: BarrierCommand) -> BarrierResult: ...
    async def close(self, cmd: BarrierCommand) -> BarrierResult: ...
    async def status(self, barrier_id: UUID) -> BarrierState: ...
```

Реализации: `HttpRestDriver` (дефолт Q3), `ModbusTcpDriver` (сухой контакт через IP-релей). Fake — только в тестах.

### Надёжность

```
timeout        3 с
retries        3
backoff        0.5 / 1 / 2 с + джиттер
circuit breaker: 5 отказов → open 60 с → half-open 1 проба
```

Каждая команда: `command_id`, `correlation_id`, `idempotency_key`, `issued_by`, `reason`. Все команды пишутся в `barrier_command` и в аудит **до** отправки, с результатом после.

Ретрай `open` безопасен (открыть открытое — no-op). Ретрай `close` — нет: можно опустить стрелу на машину. Опиши явно, какие команды ретраятся и почему; `close` по умолчанию не ретраится автоматически.

### SSRF

`barrier.endpoint` задаётся администратором tenant и используется для исходящего запроса. Обязательно:

- Аллоклист подсетей на уровне конфигурации площадки, не tenant.
- Резолв DNS до подключения и проверка полученного IP против блок-листа (127.0.0.0/8, 169.254.0.0/16, метаданные облака, ::1, локальные подсети вне аллоклиста).
- Запрет редиректов.
- Отдельный HTTP-клиент с собственным транспортом — не тот, что ходит к платёжному провайдеру.

Тест: попытка сохранить endpoint на `169.254.169.254` отклоняется; попытка подключиться к резолвящемуся в приватный IP домену отклоняется.

### Безопасность

I-8: при активном попадании в blacklist автоматическое открытие невозможно на уровне кода, а не конфигурации. Ручное открытие оператором с ролью и `reason` — возможно, с аудитом.

I-15: `POST /barriers/{id}/open` требует `reason` в теле, иначе 422.

## 4. Оффлайн-режим

**Скоуп (см. Q7 в CORE):** покрывается только недоступность PostgreSQL при живом API. Автономная работа площадки при обрыве связи с ЦОД — вне скоупа.

```
Камера → API → [PostgreSQL недоступен] → XADD в Redis Stream → 202 Accepted
                                            ↓
                              Consumer Group → PostgreSQL
                                            ↓
                                     [3 неудачи] → DLQ
```

Требования (это механизм принуждения I-4):

- Переключение — по circuit breaker на пуле БД, не по таймауту каждого запроса.
- Ответ камере — `202` с `queued: true`, не `200`. Камера должна различать.
- В Stream пишется **полный** конверт: `event_id`, `correlation_id`, `received_at` (серверное время), `retry_count`, тело, `tenant_id`, `camera_id`.
- Идемпотентность вычисляется на приёме, до постановки в очередь, и переносится в конверте — иначе после восстановления получишь дубли.
- Consumer group, `XAUTOCLAIM` для зависших pending-записей, экспоненциальный ретрай, DLQ после N попыток.
- DLQ: отдельный stream, ручной и пакетный replay через админ-API с ролью, аудитом и dry-run.
- Метрики: `redis_stream_lag`, `dlq_messages_total`, `offline_mode_active`.
- Ограничение: `MAXLEN ~` на stream и алерт при приближении. Если Redis переполняется — это уже деградация уровня «приём остановлен», и API обязан вернуть 503, а не молча терять.

**Важно:** Redis не является источником истины (§79 исходного ТЗ). После восстановления PostgreSQL порядок обработки не гарантирован — EXIT может прийти раньше ENTRY. Опиши, как это разрешается: обработка по `event_time`, а не по порядку в stream, и допущение сессий, создаваемых задним числом.

## 5. Media

- Загрузка изображений — **прямо в MinIO по presigned URL**, минуя API. API выдаёт presigned PUT с коротким TTL и жёстко заданным ключом объекта.
- Presigned GET для просмотра оператором, TTL минуты, доступ проверяется по tenant.
- Lifecycle policy бакета: удаление через 90 дней. Проверь, что policy реально применена (`mc ilm ls`), а не только описана.
- Ограничение размера на уровне бакета и presigned-политики.
- `Content-Type` фиксирован, исполняемые типы запрещены.

## 6. Gate фазы 4

```
[ ] 100 параллельных идентичных camera-событий → одна сессия, идентичные ответы
[ ] Аутентификация камеры укладывается в бюджет: замер p95 на 200 RPS вставлен
[ ] Неверный ключ и несуществующий ключ неразличимы по времени — замер вставлен
[ ] Событие с клоковым сдвигом 10 минут принимается и помечается
[ ] Событие с event_time месячной давности отклоняется как replay
[ ] image_object_key чужого tenant отклоняется
[ ] Отключён PostgreSQL → события уходят в Redis Stream, API отвечает 202
[ ] PostgreSQL поднят → все события доехали, дублей нет (сверка по счётчику)
[ ] Consumer убит на середине → XAUTOCLAIM подобрал pending, потерь нет
[ ] События, не обработанные после N попыток, в DLQ; replay через админ-API работает
[ ] Circuit breaker шлагбаума: 5 отказов → open, проба через 60 с — лог вставлен
[ ] Endpoint шлагбаума на приватный IP отклонён
[ ] open без reason → 422; с reason → запись в audit_log
[ ] Blacklist-хит: автоматическое открытие не произошло
[ ] MinIO lifecycle policy применена — вывод mc ilm ls вставлен
[ ] Общий gate §13 CORE
```
