# PHASE 08 — Тестирование

**Предусловие:** gate фазы 7 пройден.

Значительная часть тестов уже написана в фазах 2–7 — это правильно. Здесь закрываются пробелы, добавляются failure- и load-тесты и проверяется, что покрытие означает что-то реальное.

---

## 1. Покрытие

Целевое ≥ 80 % по проекту, но с оговоркой: **покрытие — не цель, а индикатор**. Дифференцированные требования:

| Слой | Покрытие | Почему |
|---|---|---|
| `tariff/domain` | ≥ 95 % | деньги |
| `billing/domain` | ≥ 95 % | деньги |
| `parking/domain` (сессии, сага) | ≥ 90 % | инварианты |
| `access/domain` | ≥ 90 % | безопасность |
| `*/application` | ≥ 85 % | — |
| `*/infrastructure` | ≥ 70 % | покрывается интеграционными |
| `api` | ≥ 80 % | — |

**Mutation testing** на `tariff/domain` и `billing/domain` (`mutmut` или `cosmic-ray`). Выжившие мутанты в денежной логике показывают, что тест исполняет код, но ничего не проверяет. Порог: убито ≥ 85 % мутантов.

---

## 2. Тесты инвариантов

Отдельный пакет `tests/invariants/`, по файлу на инвариант I-1…I-16 из §5 CORE. Каждый файл начинается с комментария: формулировка инварианта, механизм принуждения, что произойдёт при нарушении.

Этот пакет запускается в CI отдельной джобой. Падение любого теста инварианта блокирует merge независимо от остальных.

---

## 3. Интеграционные

`testcontainers`: PostgreSQL 16, Redis 7, MinIO. Никаких sqlite-подмен, никаких мокнутых репозиториев — они не ловят то, ради чего нужны интеграционные тесты.

Обязательно:

- Миграции с нуля и откат до base и обратно.
- RLS под ролью приложения (не суперпользователем — это частая и незаметная ошибка).
- Конкурентные сценарии с реальными транзакциями: параллельные ENTRY, параллельное закрытие сессии, гонка вебхука и сохранения платежа.
- Outbox: событие не публикуется при откате.
- Redis Streams: consumer group, pending, XAUTOCLAIM, DLQ, replay.
- MinIO: presigned PUT и GET, отказ при чужом ключе объекта, lifecycle.

## 4. E2E

Полный путь на поднятом docker compose:

```
въезд по событию камеры → сессия создана → шлагбаум открыт
→ ожидание → выезд → расчёт тарифа → оплата → шлагбаум
→ сессия закрыта → событие в outbox опубликовано
→ данные видны в API отчётов
```

Варианты: абонемент (без оплаты), VIP, whitelist со скидкой, blacklist (шлагбаум не открылся), низкая уверенность (MANUAL_REVIEW), ручная коррекция номера оператором, осиротевшая сессия.

Плюс E2E фронтенда (Playwright) из фазы 6.

## 5. Failure-тесты

Это раздел, который чаще всего пропускают и из-за которого потом случаются инциденты. Каждый сценарий — автотест, а не ручная проверка.

| Сценарий | Ожидаемое поведение |
|---|---|
| PostgreSQL остановлен | API отвечает 202, события в Redis Stream, потерь нет |
| PostgreSQL поднят | все события доехали, дублей нет, счётчики сошлись |
| Primary упал, standby промотирован | RTO измерен, потери принятых событий нет |
| Redis остановлен | деградация: кеш доступа мимо, оффлайн-буфер недоступен → API 503 честно |
| Redis поднят | восстановление без ручных действий |
| MinIO недоступен | событие обрабатывается, изображение помечено как недоставленное, повтор |
| Шлагбаум не отвечает | 3 ретрая, circuit breaker, сессия в нужном состоянии, алерт |
| Шлагбаум отвечает 500 после оплаты | платёж сохранён, сага в MANUAL_REVIEW |
| Платёжный провайдер таймаутит | нет повторного создания, запрос статуса, сага ждёт |
| Провайдер прислал вебхук 5 раз | один эффект |
| Воркер убит `kill -9` в середине саги | сага возобновлена, эффект один |
| Outbox publisher убит после публикации, до отметки | потребитель получил дубль, обработал идемпотентно |
| Сетевой разрыв между API и БД на 30 с | без потерь, без зависших транзакций |
| Часы камеры сдвинуты на час | событие принято, помечено, алерт |
| Одновременный ENTRY с двух камер по одной машине | одна сессия |
| Дубликат события через 10 минут | тот же ответ, вторая сессия не создана |
| Replay всей DLQ | без дублей |
| Диск PostgreSQL заполнен на 95 % | алерт до отказа записи |

Инструмент: `toxiproxy` для сетевых отказов, `docker stop` для отказов сервисов, `pytest` для оркестрации.

## 6. Нагрузочные (k6)

**Профиль обязан отражать §3 CORE, а не ровный поток.**

```
Сценарий 1 — базовый:         30 RPS событий, 1 час
Сценарий 2 — пик:             200 RPS, 30 минут
Сценарий 3 — абсолютный пик:  400 RPS, 5 минут
Сценарий 4 — heartbeat:       100 RPS параллельно со всеми выше
Сценарий 5 — операторы:       50 одновременных WebSocket + запросы к API
Сценарий 6 — soak:            30 RPS, 12 часов
```

Соотношение ENTRY:EXIT ≈ 1:1, дубликаты ≈ 5 %, низкая уверенность ≈ 3 %.

Критерии приёмки:

```
p95 POST /camera/events        < 150 ms
p99 POST /camera/events        < 400 ms
error rate                     < 0.1 %
p95 EXIT end-to-end            < 2 s
Дубликаты сессий               0
Потерянные события             0   (сверка: отправлено == в БД + в DLQ)
Рост RSS за 12 ч soak          < 10 %
Лаг репликации под пиком       < 5 s
outbox_pending под пиком       не растёт монотонно
```

Замеряй также: CPU и RAM подов, число соединений БД, latency Redis, лаг очередей, размер WAL.

**Если p95 не укладывается — не ослабляй критерий.** Профилируй (`py-spy`, `EXPLAIN` на медленных запросах, `pg_stat_statements`) и оптимизируй. Вставь профиль до и после.

## 7. Безопасность

В CI: `ruff`, `mypy --strict`, `bandit`, `pip-audit`, `npm audit`, `Trivy` (образ и файловая система), `Semgrep` (правила для Python и FastAPI), `gitleaks` (вся история, не только HEAD).

Критическая уязвимость блокирует деплой в production. Для принятых рисков — файл исключений с датой пересмотра и обоснованием; исключение без срока не принимается.

Ручные проверки, оформленные как тесты:

- Межтенантный доступ по каждому эндпоинту с ресурсом.
- Повышение привилегий подменой `tenant_id` и `role` в теле запроса и в JWT.
- JWT с `alg: none` и подменённым алгоритмом.
- Подделка camera-события без ключа и с чужим ключом.
- SSRF через endpoint шлагбаума и через `image_object_key`.
- SQL-инъекция во всех поисковых параметрах, включая номер.
- Обход RLS через прямой SQL под ролью приложения.
- Тайминговая атака на сравнение API-ключа — измерь распределение.
