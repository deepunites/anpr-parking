# Журнал событий камер под нагрузкой (v2 этап 8)

Вопрос: не замедляет ли журнал (`event_journal`, A-91) приём событий камер и не теряет ли он строки, когда поток
событий выше, чем справляется стенд.

## 1. Горячий путь: журнал не добавляет SQL

`tests/anpr/test_sql_budget.py` (3 прохода подряд после включения журнала, этап 6) — на событие камеры по-прежнему
**10 SQL в одной транзакции**, как до v2: запись журнала идёт буфером процесса и пулом bulk, вне транзакции события.
Добавление строки в буфер — **7,1 мкс** (замер ниже).

## 2. Пропускная способность записи

`tests/integrations/test_journal_throughput.py` — 10 000 строк двух клиентов через `JournalService` (буфер → пакеты
по клиенту), PostgreSQL 16 на рабочей станции (2 ядра, 3,4 ГБ ОЗУ; параллельно шла сборка .NET и Firefox, load
average ≈ 15):

```
GATE journal: enqueue 7.1 µs/row, flush 10000 rows 3.78 s (2648 rows/s), written=10000, dropped=0
```

2 648 строк/с на одном процессе API — больше целевого потока событий кластера (200 RPS на все площадки, PRODUCTION_READINESS),
причём у каждого пода API свой буфер. Буфер — 10 000 строк: даже полная остановка записи на ~1 минуту при
100 событиях/с не теряет строк; дальше — счётчик `event_journal_dropped_total` и алерт `EventJournalDropping`.

## 3. Стенд под перегрузкой: ни одна строка не потеряна

`backend/scripts/journal_load.py --rps 15 --seconds 60` против `e2e_stack.py` (API 2 воркера, publisher, consumer,
webhooks, демо-неделя в БД), 10 ключей камер (лимит 120/мин на ключ), 30 % событий — отклоняемые `LOW_CONFIDENCE`:

```json
{
  "target_rps": 15, "achieved_rps": 5.0, "requests": 900, "keys": 10,
  "statuses": {"422": 264, "200": 446, "202": 101, "503": 33, "ReadTimeout": 56},
  "accepted_ms": {"p50": 44028.4, "p95": 78755.2, "p99": 97997.0},
  "rejected_ms": {"p50": 42052.1, "p95": 72456.3},
  "journal_rows": 877, "journal_by_outcome": {"QUEUED": 115, "REJECTED": 312, "ACCEPTED": 450},
  "answered": 844, "journal_lost": -33
}
```

Машина не выдержала заданные 15 событий/с (другие задачи держали load average 15): API отвечал за десятки секунд,
часть событий ушла в оффлайн-буфер (`202`, журнал `QUEUED`), 56 запросов клиент бросил по таймауту. Главное для
журнала: **строк в журнале (877) больше, чем ответов, полученных клиентом (844)** — сервер записал в журнал и те
события, ответ на которые клиент уже не дождался; потерь нет (сверка по БД; счётчик `event_journal_dropped_total`
появился в коде после этого прогона — стенд работал на предыдущей сборке). Латентность здесь —
свойство перегруженной рабочей станции (та же картина, что в k6 фазы 8: `docs/backend/load/absolute.md`), а не журнала:
вклад журнала в горячий путь — микросекунды (§1–2).

## 4. Что проверить на staging

Повторить `journal_load.py` на staging с 3 подами API при 50–100 событий/с и сравнить p95 `POST /camera/events`
с k6 baseline до v2 (`docs/backend/load/baseline-sql-budget.md`). Ожидание: разница в пределах шума;
`event_journal_dropped_total` = 0.
