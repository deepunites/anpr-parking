### ADR-01: Модульный монолит с жёсткими границами модулей и раздельно масштабируемыми воркерами

**Контекст:** Пик 200–400 RPS событий и 100 RPS heartbeat — нагрузка для одного-двух процессов FastAPI, а не для распределённой системы; команда — один разработчик. Горячий путь ENTRY требует запись идемпотентности, сессии и outbox в одной транзакции (I-3, I-5).

**Решение:** Один репозиторий, один образ; модули по bounded context со слоями `domain / application / infrastructure`; границы охраняются AST-тестом импортов (фаза 3). API, camera-ingest, outbox publisher, stream consumer, Celery-воркеры и WebSocket-шлюз — отдельные Deployment одного образа с разным `APP_ROLE`, у каждого свой HPA, пул БД и NetworkPolicy.

**Отвергнуто:**
- Микросервисы — сетевые вызовы на горячем пути и распределённая транзакция для I-3/I-5; операционная нагрузка неподъёмна для одного человека.
- Монолит без охраны границ — границы размываются за месяц, извлечение модуля позже становится невозможным.

**Последствия:** проще — одна транзакция, один деплой, один трейс, in-process контракты между модулями; дороже — общая схема БД требует явного владения таблицами, единая версия зависимостей, масштабирование только по ролям процессов.

**Риск:** если один модуль (ingest) станет узким местом, его извлечение потребует замены in-process контрактов на сеть. Обнаруживается по p95 `POST /camera/events` и CPU-профилю подов роли `camera-ingest` (фаза 8).
