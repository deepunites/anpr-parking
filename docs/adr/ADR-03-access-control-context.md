### ADR-03: Access Control — отдельный контекст с единой точкой разрешения

**Контекст:** Blacklist, whitelist, VIP и абонемент отвечают на один вопрос — «что разрешено этому номеру на этой площадке сейчас» — и делят один инвариант приоритета (I-8). На горячем пути EXIT допустим один запрос к БД.

**Решение:** Контекст `access` владеет четырьмя видами правил и отдаёт `resolve(tenant_id, lot_id, plate_hash, at) → AccessDecision` через application-контракт. Хранение — одна таблица правил с полями «вид», «область» (`lot_id` либо глобально для tenant) и «диапазон действия»; вид-специфичные атрибуты (срок и платёж абонемента) — в сателлитной таблице того же контекста. Одна индексная выборка, один кеш, один тест приоритета. Tariff и сага только потребляют `AccessDecision`.

**Отвергнуто:**
- Четыре сущности внутри Parking — размывают агрегат сессии и требуют четырёх запросов либо UNION в чужом контексте.
- Отдельный контекст на каждый список — нет собственных инвариантов, кроме общего приоритета.

**Последствия:** проще — один запрос, одна инвалидация, приоритет в одной функции; дороже — сателлитные таблицы для абонементов, обязательный бенчмарк на 1 млн строк (фаза 3.4).

**Риск:** единая таблица не даёт p95 < 10 мс на прогретом кеше — тогда за тем же контрактом остаётся UNION ALL по четырём таблицам; контракт не меняется. Обнаруживается бенчмарком gate 3.4.
