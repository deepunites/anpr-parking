### ADR-02: Два пула соединений через две роли БД с разным `synchronous_commit`

**Контекст:** RPO = 0 для событий, сессий, платежей и outbox; RPO ≤ 5 мин для журналов и аналитики (CORE §4). PgBouncer в transaction pooling делает `SET` на уровне сессии небезопасным — переменная «утечёт» в чужую транзакцию.

**Решение:** Две роли приложения без `BYPASSRLS`: `app_critical` с `ALTER ROLE … SET synchronous_commit = remote_apply` и `app_bulk` с `off`; два пула PgBouncer. Пул выбирает use case: любая транзакция, пишущая `anpr_event`/идемпотентность, `parking_session`, `exit_saga`, `payment*`, `refund`, `barrier_command` или `outbox`, идёт через `app_critical`; `event_log`, проекции отчётов, статусы медиа — через `app_bulk`; кросс-tenant джобы (флаш heartbeat, publisher, ретеншен) — через `app_maintenance` (`on`). Аудит ручного действия пишется в той же транзакции, что и действие, и наследует её пул.

**Отвергнуто:**
- `SET LOCAL synchronous_commit` в каждой транзакции — забывается и не проверяется статически.
- Один пул `remote_apply` для всего — heartbeat и журналы удваивают латентность коммитов без пользы.

**Последствия:** проще — гарантия задаётся ролью и проверяется тестом «таблица → роль»; дороже — две конфигурации PgBouncer, RLS-политики объявляются для обеих ролей.

**Риск:** критичная таблица случайно пишется через `app_bulk`. Ловится тестом соответствия таблиц и ролей (фаза 2) и `pg_stat_statements`, сгруппированным по роли.
