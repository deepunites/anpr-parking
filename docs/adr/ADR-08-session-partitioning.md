### ADR-08: `parking_session` — HASH-партиционирование по `lot_id` (вариант A), не горячая/холодная разбивка

**Контекст:** 1 млн сессий в сутки → 365 млн строк в год; I-1 требует partial unique `(lot_id, vehicle_id) WHERE status = 'ACTIVE'`; PostgreSQL требует включить ключ партиционирования в уникальный индекс. Эксперимент на PostgreSQL 16.2 (`scripts/experiments/01_partition_unique.out`): с `lot_id` в ключе partial unique на HASH-партициях работает, без него — ошибка; `EXCLUDE` на партициях невозможен.

**Решение:** Одна таблица `parking_session PARTITION BY HASH (lot_id)`, 32 партиции, PK `(lot_id, id)`, `UNIQUE (tenant_id, lot_id, id)` как цель композитных FK из `payment`, `exit_saga`, `manual_correction`. Горячий путь содержит `lot_id` → pruning в одну партицию. Ретеншен 7 лет не требует дропа; удаление данных субъектов — анонимизация.

**Отвергнуто:**
- Вариант B (`parking_session_active` + месячные партиции закрытых) — две таблицы, перенос строки в саге, `UNION` в отчётах; выигрыш (дроп партиций) не нужен при 7-летнем ретеншене.
- Без партиционирования — индексы на 2.5 млрд строк неуправляемы.

**Последствия:** проще — один запрос, один индекс I-1, обычные FK; дороже — 32 × 6 индексов, запросы без `lot_id` идут по всем партициям, число партиций фиксировано.

**Риск:** перекос — одна площадка на 2 000 мест даёт больше строк, чем 10 маленьких; обнаруживается по `pg_stat_user_tables` партиций и `EXPLAIN` фазы 8.
